# Design source of truth

The visual design lives in a **Claude Design canvas** published as an Artifact.
This file is the contract between that canvas and the code: it records the
canvas URL, which artboard covers which screen, and the tokens FE1 implements
against.

> **Canvas URL:** https://claude.ai/artifact/LcJYjn1u6yfFENGjSfkt7J
>
> **Canvas version:** 2 · eight artboards, the demo path
> **Last synced to code:** not yet — no screen is built; Sprint 1 implements the shell and tokens first.
> **Working files:** `design/canvas/*.dc.html` + `canvas.json`, regenerated by `design/canvas/gen.py`. Edit those and re-seed; never hand-edit `traverse-ui.html`.

---

## Why both a canvas and this file

The canvas is where design happens and where it is reviewed — it renders, it is
shareable, and it can be edited visually without touching code. But a subagent
working in a worktree needs a dependency that is *versioned with the repo* and
cannot drift silently. So:

| Layer | Lives in | Owner | Changes how |
|---|---|---|---|
| Visual design, layout, flows | The canvas Artifact | Orchestrator | Edited in the canvas |
| Tokens (colour, type, spacing, radius, motion) | `web/src/design-system/tokens.ts` | **Orchestrator — frozen file** | Contract freeze, Day 1 |
| Component specs and states | This file, §4 | Orchestrator | Contract freeze, Day 1 |
| Implementation | `web/src/**` | fe1 | Sprint work |

`tokens.ts` is added to the orchestrator's frozen-file list in
[BRANCH.md](../BRANCH.md) §2, exactly like `api/contracts/**`. FE1 imports it and
never edits it. A design change that needs a new token is a **Design Change
Request**, filed the same way as a Schema Change Request (BRANCH.md §8).

## How an agent consumes it

FE1's sprint brief opens with:

> Before writing any component, read `design/DESIGN.md` and open the canvas URL
> recorded there. Implement the artboards named for this sprint. Where the
> canvas and this file disagree, **this file wins** — it is versioned with the
> code. File a DCR rather than improvising.

An agent with Artifact tool access can read the canvas directly
(`Artifact` with `action: "read"` and the URL). An agent without it works from
§4 and `tokens.ts`, which is why §4 must be complete enough to build from
alone — treat the canvas as the *rationale* and this file as the *spec*.

## 2. Design direction — settled

**Literary / warm.** Parchment-toned grounds rather than white; Literata for
anything a reader reads (character names, book titles, quoted passages); IBM
Plex Sans for interface chrome; IBM Plex Mono, tabular and oldstyle, for page
numbers, counts and confidence. One terracotta accent, used sparingly.

Three decisions worth not re-litigating:

- **The page reference is typographic, not a chip.** It is set like a
  cross-reference in a printed book — oldstyle figures, a hairline dotted rule,
  no capsule, no fill. The pill version was tried and rejected: it read as
  generic product UI in a tool whose whole subject is books.
- **Status is a dot and a word**, not a bordered pill. Aliases are an italic
  serif run separated by middots, the way a concordance sets variant forms —
  not a row of chips.
- **Relation families carry a stroke pattern as well as a colour**
  (kinship solid, romantic dashed, social dotted, adversarial dash-dot), so the
  graph survives colour-vision deficiency, greyscale, and export.

The PRD's product constraint, which the direction serves:

> This is a product about *fiction*, and the UI should feel like a reading tool,
> not a compliance dashboard. Generous line length, real typography, restraint
> with colour. The graph explorer is the only place that gets to be loud.

Non-negotiables, from PRD §6 (NFR-a11y) and the Artifact design rules:

- Light **and** dark, both defined; contrast ≥ 4.5:1 on all text and controls
- Works at 400px with no horizontal scroll
- Full keyboard navigation — the review queue's 50-tasks-in-8-minutes target
  (F5.3) is a design requirement, not just an implementation one
- The graph explorer needs a **non-visual equivalent** (a structured
  relationship list per character) — a force-directed graph alone is not
  accessible

theme in `web/src/design-system/theme.ts` is generated **from** these tokens, so
there is one source of truth rather than two.

**Browser surfaces are themed, not left to the browser** — selection, caret,
`accent-color`, scrollbar, focus ring, underline offset, tabular numerals. This
is cheap and it is the clearest signal the interface was built rather than
assembled.

## 4. Component specs

Each entry: purpose, props, every state, and its accessibility contract. Filled
at the contract freeze of the sprint that needs it. FE1 must be able to build
from this section alone if the canvas is unreachable.

### `<PageRef page={n} />` — Sprint 2
The most-used component in the product; every cited fact renders one.
States: default, hover, focus-visible, active, disabled (page not rendered yet).
Contract: it is a link, not a button. Keyboard-activable. Its accessible name
includes the book and page ("page 214 of Pride and Prejudice"), never bare "214".

### `<EvidenceItem />` — Sprint 4
Quote (≤400 chars, ETH-3), page ref, chapter, assertion badge
(narrated / dialogue / inferred), speaker when dialogue.
Contract: the assertion badge is not decoration — a `hearsay` edge must read
differently from a narrated one at a glance.

### `<RelationArc />` — Sprint 4
The temporal sequence for a character pair (F3.3). Renders a single-element arc
identically to a multi-element one, so there is one code path.

**Need:** a `surface-sunken` token for the evidence panel over the graph
**Why:** `surface` on `surface` has no separation in dark mode at 4.5:1
**Blocking:** no — shipping with a border for now
**Proposed:** add `surface-sunken` to tokens.ts, update `evidence-panel` artboard
