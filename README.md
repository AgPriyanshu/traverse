# Traverse

**Character knowledge graphs for novels — ask who someone is, get the pages
that prove it.**

Upload a novel PDF. Traverse reads it, builds a graph of every named
character and every evidenced relationship between them — typed, directed,
and temporally bounded ("acquaintance, then married, then estranged" is
three edges, not one that silently gets overwritten) — and answers plain-English
questions with a streamed, grounded answer and page-exact citations you can
click through to the actual page. Ask "how does Elizabeth know Mr. Darcy"
and get an answer with the pages that establish it, not a plausible-sounding
guess with no way to check it.

The two-Catherines problem is the one worth naming: *Wuthering Heights* has
two characters named Catherine, and a system that can't tell them apart has
failed at the one thing worth building this for. Traverse keeps them
separate, real numbers below, and the full story of why the pipeline is
built as two passes (roster discovery, then relationship extraction) rather
than one is in
[`docs/writeup-two-pass-extraction.md`](docs/writeup-two-pass-extraction.md).

## Architecture

```
PDF upload
   │
   ▼
Docling parse + page-provenanced chunking ──▶ pgvector (dense) + BM25 (lexical)
   │
   ▼
Pass 1 — roster discovery (names, aliases, honorifics → stable identities)
   │
   ▼
Pass 2 — relationship extraction, roster as a prefix-cached context,
         evidence-anchored (no edge without a page citation)
   │
   ▼
Postgres (source of truth) ──▶ Neo4j (rebuildable graph projection)
   │
   ▼
Query router → templated Cypher / hybrid retrieval → grounded, streamed
answer with inline citations — spoiler-scoped to the reader's position
   │
   ▼
Human review queue — the pipeline pauses on genuine ambiguity (e.g. two
identically-named characters) rather than guessing; a human resolves it
in seconds and the correction is never silently overwritten by a rerun
```

Postgres is the source of truth throughout; Neo4j is a rebuildable
projection used for graph traversal. Every LLM call is routed by purpose
through a live-switchable policy (`/ops/routing-policy`) with local
(Qwen3-8B, self-hosted) and frontier fallback paths.

## Run it

```
git clone <repo>
cd traverse
cp .env.example .env
make warm-models   # pre-warms the offline model cache — first run only
make up            # cold docker compose up, real API + web + Postgres + Neo4j
```

`make help` lists every target. `make up-gpu` uses a GPU-backed vLLM
profile instead of CPU inference. See `AGENTS.md` and `BRANCH.md` for the
contributor/agent workflow this was built with.
